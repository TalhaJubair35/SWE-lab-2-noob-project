\chapter*{Executive Summary}
\addcontentsline{toc}{chapter}{Executive Summary}

This comprehensive engineering report delineates the end-to-end design, implementation, and empirical verification of \textbf{LearnHub}, an extensible, academic-grade web-based learning management system. Engineered to satisfy the practical requirements of modern collegiate environments, LearnHub bridges instructional content delivery with automated, tamper-resistant assessment workflows and vibrant peer-instructor interaction.

The system is architected upon a modern decoupled web paradigm:
\begin{itemize}[itemsep=4pt]
    \item \textbf{Presentation Tier}: A Single Page Application (SPA) constructed with React 18, Vite, React Router 6, and modern CSS featuring dual-theme styling (Dark/Light), glassmorphic layout cards, animated feedback toasts, and modal overlay systems.
    \item \textbf{Application Tier}: A modular Node.js and Express services architecture enforcing role-based access control (RBAC), JSON Web Token (JWT) session authorization, password hashing with 10 salt rounds of bcrypt, and client-side anti-cheating response sanitization.
    \item \textbf{Persistence Layer}: An ACID-compliant relational SQLite database operated via \texttt{better-sqlite3}, governed by eleven normalized tables with foreign-key cascade rules and strict unique indexing.
\end{itemize}

A transparent and modular division of engineering responsibilities guided the project:
\begin{enumerate}[itemsep=4pt]
    \item \textbf{Ashiqur Rahman (Roll 2203034)} spearheaded the \textbf{Assessment and Certification Subsystem}, designing the multiple-choice question (MCQ) evaluation engine, automated real-time grading algorithms with pedagogical explanations, the \textbf{Verifiable Certificate of Completion Engine} with unique cryptographic validation keys (\texttt{LH-<courseId>-<studentId>-<HEX>}) and an open verification endpoint, and the comprehensive \textbf{Academic Learning Analytics Engine}.
    \item \textbf{Talha Jubair (Roll 2203035)} engineered the foundational \textbf{Application Shell}, \textbf{Course Discovery Catalog} with text query search and category filtering, and the \textbf{Instructor Course \& Lesson Administration Dashboard}.
    \item \textbf{Md. \end{enumerate}

Empirical verification through automated integration test suites validates a \textbf{100\% pass rate} across all functional workflows with average API response latencies below 50 milliseconds.

\chapter{Introduction and Project Objectives}

\section{Background and Context}
In modern computer science and engineering education, digital learning platforms have transitioned from auxiliary tools to mission-critical instructional infrastructure. University departments require digital tools that not only distribute lecture material but also enforce disciplined student learning trajectories through sequential curriculum checkpoints, rigorous objective testing, peer discussion, and accredited milestone certification.

Despite the proliferation of enterprise Learning Management Systems (LMS) such as Moodle, Canvas, and Blackboard, university sessional courses frequently encounter operational challenges with these incumbent solutions:
\begin{itemize}[itemsep=4pt]
    \item \textbf{Excessive Bloat and Administrative Friction}: Heavy administrative overhead and outdated user experiences deter frequent student and instructor engagement.
    \item \textbf{Rigid Assessment Pipelines}: Traditional systems often lack immediate, pedagogical feedback mechanisms that explain \textit{why} a given answer was correct or incorrect.
    \item \textbf{Opaque Credential Verification}: Course certificates are typically distributed as unverified flat PDF files susceptible to unauthorized alteration and lack independent verification mechanisms.
    \item \textbf{Disconnected Peer Collaboration}: Discussion threads and reviews are frequently isolated into disparate, poorly organized forums lacking official instructor accreditation tags.
\end{itemize}

\section{Problem Statement}
The objective of this project is to architect, develop, and test \textbf{LearnHub}, an agile, high-performance, university-grade e-learning web platform. LearnHub is specifically engineered to combine rapid course discovery, ordered sequential lesson progression, an interactive assessment engine with instant scoring and anti-cheating protection, cryptographically verifiable completion certificates, cohort learning analytics, and a vibrant community Q\&A forum into a unified, responsive interface.

\section{Project Objectives}
The concrete engineering objectives guiding LearnHub include:
\begin{enumerate}[itemsep=3pt]
    \item \textbf{Unified Course Catalog \& Sequential Learning}: Provide instant text-searchable course listings with category filters and strict lesson sequencing where students progress predictably through curricula.
    \item \textbf{Secure Interactive MCQ Assessment Engine}: Implement a client-sanitized multiple-choice assessment pipeline preventing client-side answer key inspection, coupled with instant algorithmic grading and pedagogical explanations.
    \item \textbf{Tamper-Proof Credential Certification}: Automatically validate 100\% lesson completion and synthesize verifiable credential codes verified via an unauthenticated public API endpoint.
    \item \textbf{Community Q\&A Forum \& Peer Rating}: Foster academic peer exchange with course-specific threads, highlighted instructor responses, and student star ratings aggregated into live distribution histograms.
    \item \textbf{Modular Full-Stack Architecture}: Maintain clean decoupling between the React Single Page Application and the Express RESTful API, persisted on an ACID-compliant relational SQLite store with foreign-key cascade enforcement.
    \item \textbf{Automated Test Verification}: Provide a comprehensive automated integration test suite validating every endpoint, transaction, and state transition prior to evaluation.
\end{enumerate}

\section{Software Development Methodology}
The project adopted the \textbf{Agile Scrum} lifecycle model with continuous integration and feature branching. The team executed three distinct iterations:
\begin{itemize}[itemsep=3pt]
    \item \textbf{Sprint 1 (Architecture \& Foundations)}: Establishing SQLite schema, database initialization, JWT authentication pipelines, and foundational UI layouts.
    \item \textbf{Sprint 2 (Core Subsystem Development)}: Independent modular development across assessment pipelines (Ashiqur Rahman), catalog and enrollment flows (Talha), and reviews/discussions/theme engine (Rofaz).
    \item \textbf{Sprint 3 (Integration, Hardening, and Documentation)}: Cross-subsystem integration, anti-cheating audit, automated test suite verification, and comprehensive LaTeX report compilation.
\end{itemize}

LearnHub accommodates three primary user roles:
\begin{itemize}[itemsep=4pt]

\section{Non-Functional Requirements (NFR)}
\begin{itemize}[itemsep=4pt]
    \item \textbf{Performance (NFR-P1)}: API response times must remain below 100ms under standard local network conditions. Analytical SQL queries must utilize indexes to execute within $\mathcal{O}(1)$ or $\mathcal{O}(\log N)$ time.
    \item \textbf{Security (NFR-S1)}: Passwords must be hashed using bcrypt with a minimum work factor of 10 salt rounds. Stateless session tokens must use HS256-signed JWTs. Sensitive question answer keys must never be exposed to clients prior to submission.
    \item \textbf{Data Integrity (NFR-I1)}: Database schema must enforce foreign key cascades (\texttt{PRAGMA foreign\_keys = ON}) and unique constraints preventing duplicate enrollments, reviews, or certificate issuances.
    \item \textbf{Usability and Accessibility (NFR-U1)}: The web interface must adhere to WCAG 2.1 AA standards for color contrast, provide seamless Dark/Light theme switching, and render responsively across mobile (375px), tablet (768px), and desktop (1440px) viewports.
\end{itemize}

\section{Relational Normalization Proofs}
The database design was validated against the four fundamental relational normal forms:
\begin{itemize}[itemsep=4pt]
    \item \textbf{First Normal Form (1NF)}: All relations store atomic domain values. In \texttt{quiz\_questions}, while the answer options are formatted as a serialized JSON array (\texttt{["let", "var", "const"]}), the entire set is treated as an atomic string array payload parsed exclusively at runtime, satisfying 1NF requirements without non-atomic repeating groups.
    \item \textbf{Second Normal Form (2NF)}: Every table uses an auto-incrementing single-attribute surrogate key (\texttt{id}). Therefore, no non-prime attribute is partially dependent on any subset of a composite candidate key.
    \item \textbf{Third Normal Form (3NF)}: All transitive dependencies are strictly eliminated. For example, student details (\texttt{name}, \texttt{email}) are never duplicated in \texttt{enrollments}, \texttt{quiz\_attempts}, or \texttt{certificates}; they are resolved dynamically via foreign keys linking directly to \texttt{users(id)}.
    \item \textbf{Boyce-Codd Normal Form (BCNF)}: In junction entities (\texttt{enrollments}, \texttt{certificates}, \texttt{reviews}), the candidate keys (\texttt{student\_id, course\_id}) are strictly determinants, ensuring full BCNF compliance across all relations.
\end{itemize}

\section{Transaction Management and WAL Mode Optimization}
LearnHub configures SQLite with Write-Ahead Logging (WAL) mode for maximum concurrency:
\begin{lstlisting}[language=SQL]
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
\end{lstlisting}
WAL mode decouples read operations from write operations: readers never block writers, and writers never block readers. This guarantees sub-millisecond query execution even during concurrent assessment submissions.

The grading algorithm operates in $\mathcal{O}(N)$ linear time where $N$ is the number of questions:
\begin{lstlisting}[language=JavaScript]
const attemptQuiz = (quizId, studentId, studentAnswers) => {
  const questions = db.prepare('SELECT * FROM quiz_questions WHERE quiz_id = ?').all(quizId);
  let correctCount = 0;
  const breakdown = questions.map((q) => {
    const selected = studentAnswers[q.id];
    const isCorrect = Number(selected) === Number(q.correct_index);
    if (isCorrect) correctCount += 1;
    return {
      questionId: q.id,
      question: q.question,
      selectedOption: selected,
      correctOption: q.correct_index,
      isCorrect,
      explanation: q.explanation,
    };
  });
  const score = Math.round((correctCount / questions.length) * 100);
  const quiz = db.prepare('SELECT * FROM quizzes WHERE id = ?').get(quizId);
  const passed = score >= quiz.passing_score ? 1 : 0;
  db.prepare('INSERT INTO quiz_attempts (student_id, quiz_id, score, passed) VALUES (?, ?, ?, ?)').run(studentId, quizId, score, passed);
  return { score, passed: Boolean(passed), correctCount, totalQuestions: questions.length, breakdown };
};
\end{lstlisting}

\section{Academic Viva Voce Defense Questions \& Answers}
The following ten questions address comprehensive academic inquiries during university sessional defense:

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q1: Why was SQLite selected over client-server engines like MongoDB or PostgreSQL?}]
\textbf{Answer}: SQLite is serverless, zero-configuration, and ACID-compliant. In an educational sessional environment, SQLite guarantees that database state, seed records, and relational constraints execute deterministically on any evaluator's workstation without requiring external service configuration. Furthermore, our data model is inherently relational (courses, lessons, enrollments, attempts) where foreign key cascade constraints are essential.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q2: How does Member 1 (Ashiqur Rahman) prevent students from cheating on quizzes?}]
\textbf{Answer}: When students fetch quiz questions, the backend explicitly sanitizes out \texttt{correct\_index} and \texttt{explanation} from the JSON payload. Answer keys are stored solely in the database. The client only receives the correct keys and pedagogical explanations \textit{after} the server calculates and records the student's submission.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q3: How does the certificate verification system work without a central blockchain?}]
\textbf{Answer}: When a student finishes 100\% of a course's lessons, the system generates a cryptographically unique key combining course ID, student ID, and secure random hex bytes (\texttt{LH-<courseId>-<studentId>-<HEX>}). This key is indexed with a \texttt{UNIQUE} constraint in SQLite. The public verification endpoint allows anyone with the code to verify graduate name, course title, and issue date in $\mathcal{O}(1)$ time.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q4: How does the system handle concurrent review submissions?}]
\textbf{Answer}: The \texttt{reviews} table enforces a database-level constraint \texttt{UNIQUE(student\_id, course\_id)}. If a student submits a subsequent rating, the query executes an \texttt{UPDATE} rather than an \texttt{INSERT}, preventing duplicate review inflation and ensuring statistical integrity in the 5-star histogram.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q5: What is Write-Ahead Logging (WAL) and why is it beneficial here?}]
\textbf{Answer}: In standard rollback journal mode, writing locks the entire database. In WAL mode, changes are written sequentially to a separate \texttt{-wal} log file. Readers access the original database file while writers append to the log. This enables concurrent reading and writing without database locks.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q6: How does the backend prevent SQL Injection attacks?}]
\textbf{Answer}: Every database interaction is executed using parameterized prepared statements via \texttt{better-sqlite3} (e.g., \texttt{db.prepare('SELECT * FROM users WHERE email = ?').get(email)}). Input values are transmitted separately from the SQL command structure, ensuring user inputs are treated strictly as data literals and cannot alter the SQL parse tree.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q7: What makes bcrypt preferable to SHA-256 for password storage?}]
\textbf{Answer}: SHA-256 is designed for high-throughput data hashing and can be brute-forced at billions of hashes per second using GPUs. In contrast, bcrypt is an adaptive key derivation function with an adjustable work factor (salt rounds). LearnHub uses 10 salt rounds ($2^{10} = 1024$ iterations), requiring substantial computation per attempt and rendering brute-force dictionary attacks computationally infeasible.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q8: How does React Router 6 protect routes on the client side?}]
\textbf{Answer}: Client-side route protection is achieved via a reusable \texttt{ProtectedRoute.jsx} component wrapping sensitive routes. It inspects \texttt{AuthContext}; if no valid token exists, it renders a \texttt{<Navigate to="/login" replace />} component. If a role is required (e.g., \texttt{instructor}) that the user lacks, it redirects to the unauthorized view.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q9: Why was Git chosen for version control, and how was collaboration structured?}]
\textbf{Answer}: Git provides distributed, cryptographically hashed commit tracking. Team members maintained modular branch separation corresponding to their assigned subsystems. Figure~\ref{fig:gitcommits} confirms distinct commit authorship, clean working tree states, and structured branch integration.
\end{tcolorbox}

\begin{tcolorbox}[colback=ruetblue!5!white,colframe=ruetblue,title=\textbf{Viva Q10: How are themes managed without CSS framework dependencies like Tailwind?}]
\textbf{Answer}: LearnHub uses pure Vanilla CSS Custom Properties (CSS variables) declared on the root \texttt{:root} and \texttt{[data-theme="dark"]} selectors. Switching the attribute dynamically updates all calculated color tokens across the DOM in a single paint cycle without stylesheet recompilation.
\end{tcolorbox}
